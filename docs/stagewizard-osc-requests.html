StageWand OSC Requests

StageWand — the ESP32-C6 AMOLED hardware cue controller (repo) — drives StageWizard over OSC and receives push status feedback. This document began as the wand's feature requests and is now the as-built contract both sides keep: every original ask shipped — including the color-tag follow-up — the faders question is resolved, and one new proposal is open: the Bluetooth fallback link.

Status · September 1, 2026

Everything shipped — nothing left open

P1 and P2 shipped in StageWizard v1.6.0 (released September 1) — all five status addresses with reply-to-sender subscription, /cue/{number}/select, and Bonjour from P3. The two follow-up asks landed on dev the same day (D22, 514 tests green): the liveness heartbeat and the chunked full cue-list dump, both matching the wire shapes the wand already ingests. P3 faders: resolved by Marco — scrapped. The wand's fourth page becomes a transport page (TOGGLE · STOP ALL · PANIC), which runs entirely on OSC verbs the host has had since the first OSC release: zero host changes, every control on the wand does something.
The color-tag follow-up shipped the same day (dev D27): every /stagewizard/cuelist/item now carries the cue's color tag as an optional trailing arg, and a tag edit re-bursts the list like a rename — see Cue color tags below.
New proposal (September 1, later): a Bluetooth LE fallback link so the wand keeps working when the show Wi-Fi dies — same OSC contract, tunneled over a GATT pipe, with StageWizard as the reconnecting central. Full wire spec in BLE fallback link below. (BLE-MIDI was evaluated and rejected: macOS demands a manual Audio MIDI Setup reconnect after sleep/range loss, StageWizard has no MIDI output so the wand would go blind, and the bindable verb set shrinks. Direct BLE has none of those problems.)

FOLLOW-UP  Cue color tags on the cue-list burst  SHIPPED · dev D27

The wand renders StageWizard's family palette, including the cue-tag row tints (~22% over its ground, deepened for the standing-by row, same legacy-alias mapping as CueListView.tagColor). The tag is now on the wire.

AddressArgsChangeNotes
/stagewizard/cuelist/itemi index, s number, s name, s colorTagappend one OPTIONAL argumentAs built (D27): cue.colorTag sent verbatim (red / crimson / rose / sky / steel / navy, legacy ids as stored, empty string when untagged). Fully compatible both ways: wands parse positionally, so old wands ignore the extra arg and new wands treat an absent arg as untagged. The tag is part of the host's cue-list identity, so a tag edit re-bursts the list like a rename. The wand already ingests and renders this.

BLE ASK  Bluetooth fallback link · proposed

When show Wi-Fi is unavailable, the wand advertises a BLE GATT service and StageWizard connects as a CoreBluetooth central, tunneling the same OSC messages as above, byte-for-byte — commands in, feedback out. One protocol, two transports; no BLE-specific dialect, ever.

ElementValueNotes
Service8B0F4F44-5A5B-4EC1-A0E9-77616E640001Advertised by the wand with local name StageWand-<id>. (The 77616E64 block is "wand" in ASCII.)
RX characteristic8B0F4F44-5A5B-4EC1-A0E9-77616E640002Central → wand. Write Without Response (Write also accepted). Carries framed OSC commands.
TX characteristic8B0F4F44-5A5B-4EC1-A0E9-77616E640003Wand → central via Notify. Central subscribes on connect. Carries framed OSC feedback.
Framingu16 big-endian length + OSC payloadBoth directions. Frames may split across or coalesce within writes/notifies — receivers reassemble by length. Required because macOS negotiates only ~182 usable bytes per GATT PDU and status/window can exceed that. Max payload 512 B.
BehaviorRule
Wand advertisesOnly while its Wi-Fi link is down (or BLE is forced in setup). The C6 shares one 2.4 GHz radio between Wi-Fi and BLE and Espressif marks simultaneous connected coexistence "performance unstable" — so this is a switchover, never both links hot.
Host connectsStanding scan for the service UUID whenever OSC control is enabled; connect on sight; re-issue the connect on every disconnect (CoreBluetooth connect requests never time out, so this is a free standing auto-reconnect — the fix for BLE-MIDI's manual-reconnect failure). Hold an NSProcessInfo activity assertion so App Nap never throttles the BLE loop.
SubscriptionThe BLE connection is the subscription: on connect + TX-subscribe, send the full snapshot burst (status messages, then the cue list) exactly as for a new UDP subscriber. No 5 s expiry — connection state is the truth. The ~2 s running heartbeat still flows (it doubles as the wand's liveness display).
Wand still pings/stagewand/ping every 1 s over RX — harmless, keeps one code path, and gives the host a per-wand liveness signal.
Multiple wandsOne connection each; each is its own feedback target, same as UDP subscribers.
PermissionsNSBluetoothAlwaysUsageDescription in Info.plist; add com.apple.security.device.bluetooth only if StageWizard is sandboxed.
Securityv1 unauthenticated, same trust model as the OSC listener ("enable only on a trusted show network/space"). LE pairing/bonding can be layered later without changing the protocol.
Capacity & timing (measured, ESP32-class peripheral ↔ Apple central): GATT throughput runs tens of kB/s — the 64-cue burst is single-digit kB, well under a second — and one-way latency is ~7–12 ms at macOS's ~11 ms connection interval, so GO feels identical to UDP. Wand-side status: the BLE transport slots under the existing showlink abstraction but waits for hardware bring-up (NimBLE RAM footprint, roughly 40–80 KB, must be measured in the real build — the Mac simulator cannot fake the C6 radio). The host side can be built and tested any time against a phone/ESP32 dev-board peripheral or LightBlue.

Contract

Ground rules both sides keep

Plain OSC 1.0 messages, type tags limited to i f s — exactly what both parsers accept. No bundles in feedback; each state item is its own message, so a lost datagram only stales one field until the next change, heartbeat, or subscribe-refresh. All feedback goes to every live subscriber; a subscriber is any source address heard from in the last 5 seconds. The ~2 s /status/running heartbeat is the liveness signal in both directions of trust: the wand pings every second to stay subscribed, the host re-sends so the wand knows it is alive. The cue-list burst is double-buffered begin→end on the wand and capped at 64 entries on the host. StageWand keeps HTTP /status polling as an automatic fallback whenever OSC feedback is absent.
