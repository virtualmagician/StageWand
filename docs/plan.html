Project plan · August 29, 2026

StageWand

Turning a handful of Waveshare ESP32-C6-Touch-AMOLED-1.8 boards (SKU 33305) into handheld cue controllers for StageWizard — starting with a native macOS simulator that runs the exact same LVGL C code the boards will run, so graphics and interactions are designed and tested on the Mac and flashed to hardware unchanged.

Decisions

The four calls that shape everything

UI engine
LVGL v9.5.0 (MIT)
Current stable. Waveshare's official BSP accepts LVGL ≥8 <10, so v9 runs on the boards too — one codebase, two targets.
Simulator
Native SwiftUI app
LVGL compiled into a Swift package, rendering into a CoreGraphics-backed view. No SDL, no Xcode required — builds with swift build.
Shared UI layer
Portable C target ShowUI
Screens are written once against LVGL + a tiny HAL (inputs snapshot + brightness). The Mac implements the HAL with sliders; the board implements it with real chips.
Firmware base
Official Waveshare BSP
waveshare/esp32_c6_touch_amoled_1_8 on ESP-IDF ≥5.5 — auto-detects the V1/V2 hardware revision at runtime.

Constraints

The performance envelope, in numbers

These numbers decide what a show-controller UI on this board can look like — and the simulator surfaces them live, so a design that will stutter on hardware is caught on the Mac.

322 KB
One full 368×448 RGB565 frame — 63% of all SRAM. A full framebuffer is barely possible; a double buffer is physically impossible.
368×100 px
The BSP's actual default: a single ~72 KB partial draw buffer covering 22% of the screen per pass.
~16.5 ms
Best-case full-frame push over QSPI at 40 MHz (20 MB/s) — a ~60 fps ceiling before any rendering or radio work.
0.16 ms
Cost of updating a 40×40 px widget. Partial, dirty-rect updates are effectively free — full-screen animation is not.

Design consequence: build screens from small, independently-updating widgets (meters, clocks, cue numbers, status chips) on stable backgrounds. Avoid full-screen transitions and large animated regions; one 160 MHz core runs LVGL, touch, and the Wi-Fi/BLE/Zigbee stack all at once.

Architecture

One UI codebase, two machines

ShowUI — portable LVGL C code
Screens, styles, interactions. Depends only on LVGL and showui_hal.h (battery, clock, IMU, buttons, brightness, connectivity). Never touches an OS.
▲ compiled into both ▼
macOS · AmoledSim.app
SwiftUI shell + SimBridge C glue: LVGL flushes into a CGImage-backed 368×448 canvas, mouse becomes touch, side panel fakes battery/RTC/IMU/buttons. Reproduces device quirks: single 368×100 draw buffer, even-coordinate flush rounding, DCS 0x51 brightness.
Board · ESP-IDF firmware
Official BSP (esp32_c6_touch_amoled_1_8) + a thin HAL implementation over AXP2101 / PCF85063 / QMI8658. Same ShowUI sources referenced from the ESP-IDF project.

What the simulator gives you beyond pixels

A live device-honesty readout: every LVGL flush is measured (area, bytes), and the panel shows what that frame would cost on real hardware at 20 MB/s QSPI — estimated flush time and achievable fps — plus an optional overlay outlining the dirty rectangles being redrawn. Screenshot export for design review. The Mac never lies to you about what the C6 can do.

Roadmap

Phases

  1. 01Research & verificationDone

    11-agent research fleet over Waveshare docs, official repos, community GitHub, LVGL 9.5 API, and Espressif datasheets; 5 adversarial fact-checkers confirmed the hardware profile (and corrected the I2C pin claim).

  2. 02Native macOS simulatorIn progress

    Swift package: vendored LVGL 9.5.0 + SimBridge + SwiftUI device window with peripherals panel, flush instrumentation, and PNG snapshots. Ships as AmoledSim.app; builds with swift build alone.

  3. 03Show-controller UIIn progress

    First ShowUI screens in portable C: cue screen (big GO / STANDBY), cue list, faders page, settings with brightness — dark, AMOLED-black theme with amber accents, built from small-region widgets per the performance envelope.

  4. 04Firmware bring-upNext

    ESP-IDF 5.5 project skeleton referencing the same ShowUI sources via the official BSP; flash to a board, validate V1/V2 auto-detect, measure real fps against the simulator's estimates.

  5. 05Show-control integrationNext

    Make it a real show controller: OSC over Wi-Fi 6 (with MIDI-over-BLE as fallback) speaking to StageWizard's new OSC/MIDI remote hooks — multi-device roles (GO surface, fader wing, status display), and a simulator mode that mirrors several virtual devices at once.

Risks

Quirks that will bite if forgotten

  • Two hardware revisions in the wild.Your "handful of boards" may mix V1 (SH8601/FT3168) and V2 (CO5300/CST820). Always go through the BSP's auto-detect; never hardcode a revision. Run the official 00_board_check example on each board on arrival.
  • Display and microSD are mutually exclusive.Both sit on the C6's single SPI2. Cue/show data that must be read mid-show belongs in the 16 MB flash (or over Wi-Fi), not on SD.
  • Flush areas must start/end on even x coordinates.A documented SH8601/CO5300 QSPI requirement; the BSP rounds every flush rect. The simulator reproduces this so 1-px-off artifacts show up on the Mac first.
  • No PSRAM, one core, three radios.512 KB SRAM holds LVGL, the draw buffer, Wi-Fi 6/BLE stacks, and app state together. Budget RAM per screen; prefer many small widgets over canvases.
  • Brightness is a panel command, not a backlight PWM.AMOLED brightness = MIPI-DCS command 0x51 (0–255). The HAL abstracts it; the simulator dims its canvas to match.
  • Wiki pages block bots.waveshare.com/wiki returns 403 to scripted fetches; docs.waveshare.com is the reliable mirror, and schematics/pinouts live in PDFs under files.waveshare.com.
